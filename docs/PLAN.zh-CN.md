# Agent 执行轨迹与评测数据集：收缩后的构建计划

更新日期：2026-09-24。本计划替代此前的产品与平台建设计划。当前已交付[数据集 v0.2](DATASET-v0.2.zh-CN.md)：首版研究片段保持完整，并新增实际研究运行、逐轮快照、报告版本和评审修订历史。下面的旧系统盘点保留重新规划时的基线。

## 1. 回到已经明确的要求

| 用户要求 | 本项目应执行的边界 |
|---|---|
| 参考 research-toolkit，构建自己的真实数据与合成数据集 | 从研究任务、实际运行记录、材料和产物出发，形成有来源、有结果依据的样本 |
| 新建独立闭源仓库 | 保持本仓库私有，不改造原项目为本项目的后台 |
| 个人可以运行，不再加入人力环节 | 不安排访谈、人工标注、人工复核或人工异常队列；无法自动判定的样本保留 unknown / not_assessed |
| 需要理解决策和失败机制 | 记录实际动作、观察、重试、停止及结果；保留第一次失败和后续尝试关系 |
| 先构建、跑通，再考虑盈利 | 当前不做商业验证、网站、商城、支付、订阅或获客 |
| 回溯偏移和过度工程化，重新规划 | 先减少工作范围，不以更多代码、服务或测试数量替代数据内容 |

“如何盈利”原本是分析问题。把它扩展成商城和支付实现属于执行偏移。相关本地实现和演示数据已删除，GitHub 没有上传过这些实现。

## 3. research-toolkit 具体提供哪些原料

本地只读核对版本：9b1e11fe50d55a7fdb54b0e7bb25266b49324dcb。

| 原项目资产 | 用途 | 不能直接声称的属性 |
|---|---|---|
| evals/cases 下的 7 个任务定义 | 任务目标、读者、材料、产物和覆盖要求 | 它们只是任务定义，不是 7 条真实运行 |
| regression_fixtures 的 22 个反例 | 已知异常条件与判定器回归素材 | 构造反例不等于模型实际犯错 |
| conformance_fixtures 的 4 个控制样本 | 正常路径与边界对照 | 控制通过不代表研究结论真实 |
| semantic_diagnostics 的样本与评审记录 | 主张、证据和表达问题的候选标签 | 模型评审不能直接升级为确定事实标签 |
| 已有研究运行的任务、来源表、主张表、评审与最终产物 | 建立任务和结果之间的关联 | 这些文件本身不能补出缺失的工具调用 |
| 明确指定的实际运行日志 | 可见动作、工具返回、错误与终止的原始证据 | 缺失日志和隐藏推理不得事后补写 |

一个任务定义要求的典型文件包括 state/task_spec.md、state/progress.json、data/source_registry.csv、data/claims_registry.csv、logs/review.jsonl 和 final.md。下一步应把这些内容与同一次运行的可见事件对齐，而不是继续以程序自己的批次汇总生成问答题。

来源材料和已有模型输出各自保留用途边界；闭源状态不能替代数据来源说明。当前不向外发送私人日志或研究材料。

## 4. 首批数据以一个任务片段为最小单位

采用“Agent 执行轨迹与评测数据集”这个名称。Runtime 是执行环境；trajectory 是实际执行留下的事件序列。

每条可用样本至少能定位：

1. **任务**：原始目标、约束、所属研究任务、起止边界。
2. **输入与环境**：当时可见材料、工具定义、实际返回或可重放快照。
3. **事件**：可见模型动作、工具请求、工具结果、产物引用、先后顺序。
4. **结果**：最终产物、终止原因、pass / fail / not_assessed。
5. **判定依据**：执行了哪个规则、依据哪些证据、哪些属性仍无法判断。
6. **血缘与用途**：原始来源、文件哈希、父样本、合成配方、切分、允许用途。

使用已有任务、事件和运行格式，先补齐字段映射，不创建新的通用工作流框架。运行时没有提供的理由留空，不生成“内部决策过程”冒充原始记录。

真实任务、合成任务、真实执行、脚本执行分开标记。模型实际跑过合成题可以称为真实执行轨迹，其任务来源仍然是 synthetic。

## 5. 最小构建路线

### 第一步：整理真实来源与现有样本

只处理已明确选定的自有运行和研究产物。生成统一清单，登记每条数据的任务来源、执行主体、完整度、可验证结果和用途。

对缺失事件、缺少最终产物或无法对应同一次运行的记录保留原样，标记为部分记录。不会为了增加“真实数据”数量，把框架模板、问答脚本和不完整会话计为完整任务。

**完成条件：** 每条候选记录都能回到源文件；已知缺失和无法判定项都有机器可读原因；脚本、模型、真实会话分母明确。

### 第二步：跑通一个有完整依据的任务片段

从原项目已有研究任务中选择可由程序核验的片段。优先考虑引用是否存在、主张是否受给定材料支持的结构化部分、来源缺失处理和工具故障恢复。开放式报告的洞察与文风暂不设确定性总分。

如果现有日志不具备完整环境，只归档为观察记录；需要重跑的任务另建运行，明确标记 replay，不能冒称原始任务的完整回放。

先完成一条端到端样本，再扩展到少量不同失败机制。现有虚构产品属性题继续作为执行器回归用例，不继续靠改名称、改数值扩充主数据集。

**完成条件：** 输入、动作、结果、判定证据串联完整；正控制、错误控制和证据不足控制能够被区别；同一冻结输入的验证结果可复现。

### 第三步：从这些任务派生合成变体

为已有任务设计少量能解释用途的变化：来源缺失、过期材料、相互冲突的证据、工具暂时失败、必要字段缺失。每次变形都记录父样本和改动。

合成题重新计算答案，重新运行、重新判定。未运行的题只进入任务候选集；程序生成的预期动作只标为脚本控制。若种子运行没有失败，就写成“从已观察运行派生的故障注入”，不能称为“真实失败扩增”。

**完成条件：** 父子关系、变化条件和标签来源可追溯；不是仅靠改 ID 增加条数；重复样本合并或明确标识。

### 第四步：形成一个可复核的数据集版本

复用本地 Python、JSON/JSONL 和文件目录，形成一份数据包：任务、环境、事件、结果、切分清单、数据说明以及验证入口。

同一原始任务、来源快照、重试链和合成派生全部留在同一切分。任务数较少时，不把少量 holdout 的通过率解释为泛化证据；共享模板的切分也不等于跨机制泛化。

**完成条件：** 从零读取数据包可以完成验证；导出前后数量一致；无父子样本跨切分；坏样本被拒绝；不把未执行、不完整或用途不符的记录混入训练集。

## 6. 自动决策与失败处理只保留必要规则

| 情况 | 数据处理 |
|---|---|
| 临时工具失败 | 在既定预算内有限重试，保留第一次错误和全部尝试 |
| 明确错误答案 | 保存 fail；后续尝试另建记录并关联父 run |
| 证据确实不足 | 依据任务规则判定合理弃答，不要求强行产出答案 |
| 轨迹缺失或环境无法还原 | 标记不完整 / not_assessed，不伪造参考答案 |
| 标注规则无法判断 | 保留 unknown；不建立人工处理队列 |
| 数据重复或家族跨切分 | 拒绝入选该版本，并记录原因 |
| 步骤、时间或调用预算耗尽 | 停止；未完成不能记为通过 |
| 用途不允许 | 拒绝对应导出，不改变原始记录 |

第一阶段以确定性规则为主，不新增多模型裁判服务。来源、主张和引用中能程序核对的部分先核对；需要主观研究判断的属性保持未评定。

## 7. 现有工程怎样收缩

| 处理 | 内容 |
|---|---|
| 保留并复用 | 来源采集、事件记录、冻结任务、有限执行、确定性验证、失败保存、去重与家族切分 |
| 保留为历史样例 | 300 条模板题、已有脚本控制、5 条模型运行、不完整真实会话和独立评测包 |
| 暂停并退出主流程 | 后台常驻、目录轮询、定时扩产、HTTP 评测服务、客户端额度、服务端交付管理 |
| 本阶段不新增 | 平台前端、账户系统、数据库服务、云队列、多租户、训练平台、商业验证 |
| 已删除 | 偏离任务新增的商城、支付、网页、配置、测试、订单模拟数据、试用包、4 条演示运行及截图 |

已有 API、服务和相关测试保留在历史实现中，当前不启动、不继续开发，也不作为数据集验收条件。这次不进行第二次大规模重构，以免继续把时间花在平台代码上。

## 8. 如何判断这次真的完成

完成标志是一份可以直接检查和验证的数据集：来源清楚、真实与合成分开、轨迹可对应任务、错误没有丢失、标签有依据、派生不泄漏、验证能复跑。

当前状态：四步已跑通并交付 v0.1、v0.2。v0.2 新增 4 次实际研究运行、8 轮与 646 条事件、98 份产物快照、8 个报告版本；另接入 8 次历史语义评审调用与 104 条判断。原稿、反馈和修订稿已有机器可读关联，原失败与旧版本保持不变。本轮新增模型调用为 0，完整数据包可离线验证。

本阶段交付的是开发诊断数据集。两版共享两组研究来源；网页返回正文仍缺失，后期修稿没有完整作者运行轨迹，未见测试和训练导出均为 0。后续扩充以补齐实际观察和新增来源为准，不通过扩大模板数量或增加平台功能代替内容建设。
