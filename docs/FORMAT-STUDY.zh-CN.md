# 格式修复补充实验：记录更准确，文本接口仍有明显损耗

2026-09-29。32 条首次执行全部进入终态，逐条重放核验通过；按当前环境评分，31 条成功，1 条因交付内容结构错误失败。成功执行包括 23 条正确完成修订、8 条正确阻塞。GLM 全程使用 Coding Plan。

新采集器已消除“有效动作仅因缺少理由而被拒绝”的问题，并分开记录模型理由、缺失情况和采集器错误。加入一个 JSON 例子后，理由缺失明显减少，但仍有大量格式拒绝。当前可以确认的是采集记录的完整性与来源标注得到改善，业务能力提升仍缺乏充分证据。

## 两个条件的实际结果

N 使用修复后的接口、公共工具和规则，无格式示例。E 在同样输入中加入一个读取 policy 的合法 JSON 动作例子，不提供业务示范。四家各运行同样四个开发任务 × 两条件，每格一次，条件顺序按任务交错，共 32 条。各执行状态与模型上下文独立，没有择优重跑。每条最多 48 个模型回合，单回合最多三次服务调用尝试。

| 条件 | 评分成功 | 模型回合 | 实际环境动作 | 格式拒绝 | 有效动作中理由缺失 | 上报输入 token |
|---|---:|---:|---:|---:|---:|---:|
| N 无示例 | 15/16 | 334 | 266 | 68 | 141 | 934,600 |
| E 单个格式示例 | 16/16 | 312 | 256 | 56 | 9 | 841,240 |

E 合计少 22 个模型回合，其中 12 个来自较少的格式拒绝，10 个来自较少的环境动作。有效动作中缺少理由的比例从 141/266 降至 9/256。理由字段有文字不等于理由正确；本轮没有对其语义质量评分。15/16 与 16/16 的差别只对应一个失败样本，不能据此声称可靠的成功率提升。

| 模型 | N → E 成功数 | N → E 模型回合 | N → E 格式拒绝 | N → E 理由缺失 |
|---|---|---|---|---|
| DeepSeek deepseek-flash | 4/4 → 4/4 | 83 → 70 | 12 → 6 | 42 → 0 |
| Kimi kimi-k3 | 4/4 → 4/4 | 65 → 63 | 3 → 1 | 12 → 0 |
| GLM glm-5.3 | 4/4 → 4/4 | 77 → 77 | 8 → 9 | 42 → 0 |
| LongCat LongCat-2.0 | 3/4 → 4/4 | 109 → 102 | 45 → 40 | 45 → 9 |

效果并不一致：GLM 总回合没有减少，格式拒绝多一次；LongCat 在首题和缺失材料题加入示例后反而有更多格式拒绝。LongCat 的 harbor-backlog-N 用满 48 回合后成功提交，其中 30 次为格式拒绝、18 次为真实环境动作。没有因达到上限而中断的执行。

本轮保留 646 个可见输出对应的模型回合、522 个环境动作、649 次采集器层调用尝试。Kimi 有三次 HTTP 200 且 finish_reason=stop、但可见内容为空的响应，都在原回合重试后恢复；根因未确定，不称为网络故障。全部尝试均返回了用量。上报输入/输出合计为 1,775,840 / 232,003 token。该口径包含重试，不等于货币账单，跨供应商 token 也不能直接解释为同质成本。

## 修复了什么，哪些问题仍在

1. 外层 JSON 的必需字段为 tool 和 args；decision_summary 可以缺失或为 null。原 901 次输出离线重解析时，743 个原有合法动作保持不变，158 个原拒绝中有 44 个因此可解析。这只是离线解析审计，不是 44 次新增成功执行。
2. 模糊输出、重复 JSON 键、多个动作、不允许的工具和非对象参数不会执行。原始可见文本与具体错误进入下一次公开请求；格式拒绝不会伪造为环境的 unknown_tool。
3. 模型的可见理由、理由缺失和采集器反馈有不同来源字段。本批有 372 个带理由的有效动作、150 个无理由的有效动作、124 个采集器拒绝回合；不会用系统编写的错误说明填充模型理由。
4. 格式拒绝消耗一个模型回合、不执行环境动作。两种计数分列，因此不能通过移出拒绝记录制造“步骤下降”。拒绝没有环境奖励；对应环境事件索引为 null。有效动作的奖励从所链接的 episode.events 读取。
5. 剩余 124 次外层拒绝中，8 次明确识别为 DSML 标记，116 次为其他不合法 JSON，后者包含 LongCat 工具标记和 JSON 后附加说明。本轮仍采用文本输出通道，尚未解决供应商原生工具格式与本地动作接口之间的完整适配。

## 一条真实失败如何记录

`runs/longcat/cedar-pilot-N/` 保存了唯一评分失败。数值 74 和结论 further_pilot_required 均正确，但结果被写成 `{"result":{"value":74,"unit":"percent"}}`，缺少约定的 success_percent 输出名称；正确结构应为 `{"result":{"success_percent":{"value":74,"unit":"percent"}}}`。这是交付内容契约失败，不应称为计算错误。

按实际环境步骤核对：第 10 步写坏了 analysis.json 的保护文字大小写；第 11–12 步重读两份文件；第 13 步再次编辑，恢复保护文字。第 14 步 validate 因修改后尚未重读而失败，第 15–16 步补读后，第 17 步 validate 通过。第 20 步提交后，最终评分仍因输出名称缺失给出 0 分。该轨迹有三次被接受但结果结构错误的写入，仍只算一条任务失败。

因此可以记录重读后的局部修正、校验失败后的补读与再次验证，也必须保留最后未修好的问题。这里的“校验通过”仅覆盖公开的一致性检查，不能替代最终内容评分。没有将原失败重跑成成功，也没有把局部修复描述成整条任务成功。

## 与旧完整轨迹实验的关系

旧 C 条件的 16 条执行为 266 个模型回合、249 个扣除格式拒绝后的环境动作、17 次格式拒绝、2,467,220 个输入 token。新 E 为 312 回合、256 个环境动作、56 次格式拒绝、841,240 个输入 token：输入约少 65.9%，回合多 17.3%。短例减少上下文体量，但并未在本次观察中达到旧完整示范的回合表现。

旧 A/B/C 与新 N/E 同时改变了采集器、提示及调用时间，不能把这些差别归因于示例长度，更不能把接口修复或记录补全当作业务推理提升。新旧两批共 80 次诊断执行，仍只基于同四个使用构造材料的开发任务，不能记为 80 个独立任务。

本批未启用供应商的原生结构化输出。DeepSeek 官方说明列出了 response_format 的 JSON Output 模式，并提示可能返回空内容；这支持下一步先做小规模接口验证，尚不证明其在本配置下的实际效果。[官方说明](https://api-docs.deepseek.com/guides/json_mode/)

## 数据边界与复算

任务使用原创构造材料，轨迹来自四家官方模型服务的实际调用，不代表真实企业历史。请求仅包含公共观察、历史和指定语法例子；场景隐藏状态、参考解、评分答案、凭据和隐藏推理未进入模型输入。供应商返回的模型标识与请求配置一致，按实际调用记录报告。

所有新增执行均为 development/diagnostic、training_eligible=false。未自动加入训练集；历史 14 条可训练示范和 v0.16 消费包中的 7 条示范不因此增加。每格一次、同作者与工作流模板、重复使用开发题，均限制了效果解释；本轮记录的是这些既有独立任务的实际执行，未测量跨场景泛化。

数据目录为 `data/format-study-20260929/`。freeze.json 固定输入与采集代码；prior-parser-audit.json 保存旧输出的离线复查；runs/ 保存每回合请求、全部响应尝试、解析反馈、执行轨迹和最终文件；analysis.json 保存复算、失败和局部恢复定位。旧版 48 条数据和冻结代码保持原样。

六项针对性测试通过，覆盖不误拒缺失理由、拒绝歧义而不修改环境、错误反馈及来源、允许的封装、工具参数错误归属，以及含服务重试和格式修正的完整本地流程。未重跑旧版全套测试。32 条实际记录已核对精确公共输入、输出到动作的对应、环境重放、终态评分、交付文件与用量。
