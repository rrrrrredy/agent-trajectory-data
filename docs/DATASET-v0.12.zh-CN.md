# v0.12：修复完整分母与最终可用性汇总

更新：2026-09-29。本版新增一个原创合成程序修复任务，已完成一次实际模型首次执行：13 次调用，终局奖励为 1。模型修复了错误的结果汇总函数，也在一次违反读取规则的修改被拒绝后完成恢复。243 项回归、8 项独立解包执行与行为检查通过，17 类重算哈希后的篡改被拒绝。完整包见 [v0.12 私有发布](https://github.com/rrrrrredy/agent-trajectory-data/releases/tag/dataset-v0.12)。

这次补的是一个具体能力：模型能否修复把局部标签当作最终可用、把失败尝试从统计中删掉的程序。既有采集器已经保留完整任务分母；本任务进一步检验模型写出的汇总函数是否遵守这些要求。它复用现有有界 Python 修复环境，没有增加环境工具，也没有新增通用评分体系。

十八个用例属于同一个任务，不能算成十八个独立任务、来源或实验。一次成功也不能据此估计模型在其他企业、其他代码库或开放式研究任务上的成功率。模型身份来自请求配置，客户端没有提供供应商签名证明。

函数比较同一份预注册任务清单下的基线和候选。两侧都必须每个任务恰好一条记录，缺失、重复或未知任务 ID 抛出 `ValueError`。最终可用量只按 `status` 统计，`label_pass` 只代表局部检查。所有尝试的实际耗时，包括失败等待，都进入总耗时；不可用任务 ID 留在输出中。

本题采用明确的保守接受规则：候选至少产生一个可用结果，基线已有的可用任务全部保留，总耗时不增加，并且可用任务增加或总耗时严格下降，才判为改善。因此，十个可用结果变成两个更快的结果应拒绝；全部失败只是失败得更快也应拒绝；完整交付且确有改善应接受。这个规则是本题的既定政策，不代表所有业务都必须使用同样的取舍。

五条语义错误控制分别模拟一律拒绝、局部标签替代最终状态、只累计成功耗时、只比较可用数量和只比较任务 ID 集合。最后两项有各自针对的反例：可用数量不变却丢失原来可用的任务，以及记录包含全部 ID 却额外重复成功记录。另有一个部分修复程序通过两个公开样例，但在七个覆盖完整性用例上失败。现有过程控制继续检查未复现初态故障、未复测、测试后又修改、错误回执绑定等问题。

本次实际执行保留了以下过程：

1. 第 1—3 步读取策略、契约和原程序；第 4 步运行公开测试，观察到初态失败。
2. 第 5 步补上任务清单非空、唯一的检查，修改成功。
3. 第 6 步再次修改时虽然携带当前版本号，但尚未复读更新后的程序，收到 `412 read_current_worker`。这是模型违反既有动作规则产生的真实错误，没有注入并发故障。
4. 第 7 步复读当前程序，第 8 步合并其余修复：严格核对双方任务覆盖、保留全部耗时、依据最终状态统计，以及实现完整接受条件。
5. 第 9 步复读最终程序，第 10 步公开测试通过；第 11—13 步填写绑定最终代码与测试的说明、更新任务并提交。终局独立隐藏检查通过。

这条轨迹中，初态测试失败是任务要求的复现，412 是模型操作失误，两者分别记录。完整失败导出新增这两个事件及对应恢复。不能把一次 patch 返回 200 当成程序已修好；最终成功还依赖当前代码的公开测试、隐藏行为检查、读取时序和提交绑定全部成立。

在仓库根目录可以启动同一个环境：

```powershell
py -3 -X utf8 -B scripts/repair_env.py data/runtime-batch-v0.12/tasks/repair-denominator-integrity-clean-v1/scenario.json --output ../denominator-episode-v12.json
```

进程先输出初始观察，此后每行接收一个 `{tool,args}` JSON 动作。例如读取公开契约：

```json
{"tool":"read","args":{"document_id":"contract"}}
```

整包组装后，从解压包根目录核验实际轨迹或执行参考策略：

```powershell
py -3 -X utf8 -B runtime_release.py verify .
py -3 -X utf8 -B task-entrypoints/repair-denominator-integrity-clean-v1/tests/verify.py model/episodes/repair-denominator-integrity-clean-v1/episode.json
```

运行需要 Python 3.10+；环境本身无外部依赖、无需联网。策略只接收公开 reset/step 观察，隐藏用例、参考代码和错误控制留在评价侧。模型不能向 `test` 传入自己设计的实验，隐藏失败也不会在提交前反馈；本版不把这两项未具备的能力算入覆盖。
