# 三份资料对两个仓库的实际帮助

查阅：2026-09-28；按现有实现复核：2026-09-29。这次最有用的发现是一个具体判断错误：只看成功样本的耗时，或把局部检查通过当成最终可用，都可能让坏结果被评为改善。它值得成为可复现的诊断材料；它并不意味着两个仓库都需要增加一套评分机制。

Anthropic 原文的可取之处是先确认测量对应真实完成的工作，再逐项修复并保留回归检查。文中速度收益属于作者团队的特定产品和条件，不能外推成我们的研究流程收益。[原文](https://claude.dev/blog/how-we-made-claude-ai-faster/)

网易文章中“写作风格距离改善、文本感受却变差”和同稿模型评分不稳定的例子，提醒我们检查评分是否评价了目标本身。这些是作者的经验陈述；对我们有用的行动是复查已保留的失败，不能直接搬来指标或把一次最高分设成后续硬下限。[网易文章](https://www.163.com/dy/article/L7O1CMKT0556BKW5.html)

huashu-flash 提供了一个可以实际复现的检查缺口。本次固定在提交 `94a06d0e954836226ca54b0d67a2f4c41f4ea1d3`：`bench.py` 只用成功运行计算分位数，`ratchet.py` 读取 p75 时没有同时约束成功次数。用纯合成输入复现，基线 10/10 成功、耗时均为 100；候选只有 2/10 成功、成功样本耗时为 50，其余八条失败，仍通过默认速度检查。这证明的是两个函数组合的检查缺口，没有重测作者的网站，也没有否定其性能结果。复现回执见 [checker-review.json](../artifacts/huashu-flash-checker-review.json)。[测量脚本](https://github.com/alchaincyf/huashu-flash/blob/94a06d0e954836226ca54b0d67a2f4c41f4ea1d3/scripts/bench.py#L108) [阈值脚本](https://github.com/alchaincyf/huashu-flash/blob/94a06d0e954836226ca54b0d67a2f4c41f4ea1d3/scripts/ratchet.py#L31)

toolkit 已保留一个同类错误，值得直接连接这次发现。2026-09-08 的评审记录中，DeepSeek 和 Kimi 的首轮 80 个片段判断都同意作者的标签，却同时漏掉一条错误正例：把四个通过标签检查的候选视频，算成四个完整可用的视频结果，并据此分摊成本。修订后只承认“至多四个标签合格候选”，缺少整体可用性和成本输入时不计算完整单位成本。这里真实发生的是模型评审漏判；被评审的输入本身是合成诊断片段，不能叫四个真实视频生产任务。原始输入、判断、修订和复审均独立保留。[固定版本的评审记录](https://github.com/rrrrrredy/research-toolkit/blob/28524448eaf6534125a24dd1ea26e986016c8aea/evals/semantic_diagnostics/reviews/2026-09-08/README.md)

这个关联给 toolkit 的具体帮助是：评价“有效完成量”时，要核对其判定条件和完整分母；多名评审一致也不能替代这个核对。上述缺陷在 toolkit 中已有修订，本轮没有依据重新修一遍，也不能把旧题修订包装成新的留出效果。若以后相同错误在当前版本重现，应先用保留输入复现，区分规则未执行、规则遗漏和评审器误判，再修改对应位置。

数据集仓库也已有相关防护，必须先承认这些覆盖：

| 问题 | 当前已有证据 | 本轮处理 |
|---|---|---|
| 公开检查通过，但交付结果错误 | v0.11 的 `wrong_result` 负例公开校验通过，终局奖励为 0；[测试](../tests/test_workspace_runtime.py)核对独立结果评分 | 保留，不再新增同义负例或第二套评分器 |
| 修补通过公开样例，却仍在其他输入上出错 | v0.10 的 `manifest-hashes/partial_fix` 公开测试通过、隐藏行为测试失败、奖励为 0；[测试](../tests/test_repair_runtime.py)已覆盖 | 保留，不以更换数字或布局冒充新能力 |
| 失败尝试从统计分母消失 | [collector](../scripts/runtime_collect.py)核对输出任务序列与完整配置一致；[workspace 导出](../scripts/workspace_exports.py)保留每条奖励、终止状态和停止原因，并分别统计正常交付与合理阻塞 | 本次未发现成功样本过滤漏洞，不新增通用指标框架 |

上表来自代码和冻结负例记录的复核，不是新增模型实验。训练用的成功示范会按条件筛选，但完整运行记录仍保留失败；不能把成功示范数当作全批成功率。合理阻塞也不代表已产出可交付报告。

仍有两个能力边界：[repair_env 的 test](../scripts/repair_env.py)只运行固定公开用例，模型不能传入自己构造的新检验；隐藏用例只在提交后评分，模型也不能看到该失败后继续修复。v0.11 的证据更新在首次写入时触发，不能宣称覆盖“修复验证通过后，新输入使问题再次出现”。扩展这些能力需要改变环境行为，目前没有必要为了对应文章先做扩展。

后续只保留一个具体候选：**核对完整尝试记录及最终可用条件的纯函数修复任务**。可以复用现有程序修复环境，让模型修复一个错误汇总函数：它只看成功记录，或把标签通过直接算作完整可用。任务应至少能区分以下行为：

- 10 次尝试中仅两次最终成功，不能因这两次更快就接受候选。
- 全部既定任务记录齐全、完成条件相同且确有改善时，可以接受，防止“一律拒绝”得分。
- 删除失败记录、重复成功记录，或仅有局部合格标签时，不能伪造完整分母和最终可用数。

该候选现已在 [v0.12](DATASET-v0.12.zh-CN.md) 实现为一个原创合成修复任务，并完成一次实际模型首次尝试：13 次调用，最终代码通过 18 个行为用例。它未计入 v0.11 的任务、覆盖或完成结果。其来源可以绑定上述公开检查复现及 toolkit 的历史评审漏判，但函数、输入与扰动须另标为合成构造；真实评审记录、合成任务、参考执行与实际模型运行分别保存。以后若导入历史源记录，继续继承原有用途、分割和训练限制，公开可读不自动等于可用于训练。这项任务也不能被描述为已经评价了模型自行设计实验的能力。

原先“两家族、各三个变体”的固定数量计划撤回。只有出现现有用例无法表达的失败、能明确写出正确与错误行为，并能用现有环境或小幅扩展验证时，才值得新增任务。若已有负例和评分已能捕捉问题，或新增内容只是换数值、文件名、再重复一项原则，就不改。v0.11 已完成采集和验收，v0.12 只落实上述一个必要增量；文章带来的价值在于找到上述可核对的错误机制，并排除重复建设，而不在于增加文件、测试或任务数量。
