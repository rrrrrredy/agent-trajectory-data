这些建议需要接在已有实现上。toolkit 的现行文档已经区分机械符合性与研究质量，要求条件匹配的配对比较、保存原始失败和对评审意见逐条核查。优先工作应是为一项明确的产品改进补出可复核的执行证据。相关现状见 toolkit 仓库的 `docs/evaluation-status.zh-CN.md`、`docs/evaluation-roadmap.zh-CN.md` 和 `docs/report-evaluation-standard.zh-CN.md`；本次核对的提交是 `28524448eaf6534125a24dd1ea26e986016c8aea`。

代码审阅还复现了一个值得保留的反例。bench.py 的分位数只使用成功运行；ratchet.py 读取 p75，没有同时约束成功次数。我构造了两组纯合成输入：基线 10/10 成功、耗时均为 100；候选仅 2/10 成功、成功样本耗时为 50，其余八条失败。候选仍通过默认速度检查。这证明的是这两个函数组合的检查缺口，没有重测作者的网站，也没有否定其性能结果。复现回执在 `artifacts/huashu-flash-checker-review.json`。[测量脚本](https://github.com/alchaincyf/huashu-flash/blob/94a06d0e954836226ca54b0d67a2f4c41f4ea1d3/scripts/bench.py#L108) [阈值脚本](https://github.com/alchaincyf/huashu-flash/blob/94a06d0e954836226ca54b0d67a2f4c41f4ea1d3/scripts/ratchet.py#L31)

因此，我们应并列记录：全部尝试的成功或失败、严重结果缺陷、合理阻塞、模型或传输失败、预算截断，以及成功样本的耗时和可见 token。失败分母不能消失。合理阻塞表示正确处理了缺失证据，不表示产出了可交付报告。对于随机模型输出，不能把一次最优分数设成以后每次运行的硬下限；确定性的回归错误可以严格阻断，带噪声的效果判断需要重复和配对证据。

v0.11 已有十二个有界任务，涵盖两个归档报告来源与四个合成来源，并核验版本、引用、文件一致性及不确定写入恢复。它还没有评价开放式研究质量，也没有要求模型自己设计一个有效的检验。这个缺口适合成为后续数据批次的切入点。

建议下个小批只增加两个机制家族，每家先做三个变体：

1. **指标误导与候选拒绝。** 提供一次看似提速或提高覆盖率的修改，但完整记录暴露失败增加、范围缩小或关键输出丢失。模型需要设计检查、核对所有尝试并拒绝不合格候选。有效对照应允许保留真正改善的候选，防止“全部拒绝”得分。
2. **修复后的回归。** 初次修补在已知例子上通过，另一个输入或环境变化使问题再现。模型要定位失效条件、修改、重新验证新旧任务，并留下能够再次捕捉该缺陷的检查。来源和家族固定切分，模型实际观察之前不提供后续结果。

新家族复用已有事件和文件结构，补足可见的假设、预测、工具检验、观测结果、保留或拒绝决定、独立复验。参考执行、合成扰动和实际模型轨迹继续分开。先用脚本正反例验证评分是否可靠，再进行已界定预算的模型采集。

toolkit 的后续改进可从上述任务或已保留的真实失败中选一个具体问题，解释它属于方法遗漏、已有规则未执行、工具缺陷还是评审误报，然后只修改对应部分。每次比较保持任务、证据条件和结果标准可比；从旧题中得到的修复反馈属于开发或回归证据，不能再包装成新的留出效果。

两个仓库的分工保持清楚：toolkit 承担研究执行方法与框架修复；数据集仓库承担任务、来源、环境、轨迹、评分和导出。结果通过固定版本与来源引用相互关联。采用上述小批实验，应优先观察能否增加有效的新问题与可复验恢复链；单纯增加变体数、测试数或文件数不作为进展目标。
